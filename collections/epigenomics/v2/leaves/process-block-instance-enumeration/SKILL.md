# process-block-instance-enumeration

## Summary

Enumerates the subtask instances generated by Watchdog's process block mechanism from an XML workflow definition, where each process block (sequences, folders, tables, or upstream task return values) expands to one subtask per instance with placeholders replaced by the instance's variable values.

## When to use

Use when a Watchdog XML workflow task definition contains process blocks (process sequences, folders, or tables) and you need to determine or reconstruct the exact set of expanded subtask instances.

## When NOT to use

- The workflow XML contains no process blocks (e.g. example_basic_sleep.xml with a single task, or example_dependencies.xml) — no instance expansion is needed
- You need to design or edit modules rather than expand task instances — use the moduleMaker or workflow designer instead
- You need to validate module or workflow integrity rather than enumerate instances — use moduleValidator.jar or workflowValidator.jar

## Inputs

- Watchdog XML workflow file (e.g. example_process_blocks.xml) containing process block definitions
- Watchdog installation folder configured via configureExamples.sh (providing the examples subdirectory)
- For folder blocks: filesystem paths or file patterns matching the block specification
- For return-value-driven blocks: output/return values of preceding tasks in the workflow

## Outputs

- Complete instance/subtask set per process block, i.e. one expanded subtask per instance with placeholders substituted
- Tab-separated table of expanded subtasks (e.g. process_block_instances.tsv, one row per expanded subtask)

## How to apply

Load the shipped example workflow example_process_blocks.xml, generated into the examples directory by running ./helper_scripts/configureExamples.sh -i /path/to/install/folder/of/watchdog. Parse the XML process block definitions and identify all placeholders according to the block types illustrated by the example: process sequences, folders, and tables. For process sequence blocks, enumerate every sequence element and substitute each into the task instance pattern; for folder/file-pattern blocks, enumerate matching paths as instance placeholders; for table blocks, expand one instance per table row, substituting row fields. For blocks driven by return values of preceding tasks, link each instance to the upstream task's returned value. Rationale: Watchdog process blocks define a set of instances, each holding one or more variables, and exactly one subtask is created per instance, so the expansion is deterministic given the XML definition.

```

```

## Evaluation signals

- The script runs without error on the XML workflow file (e.g. via ./watchdog.sh -x path2/xml-file.xml)
- The output TSV exists and contains one expanded instance row for every block definition present in the example, covering process sequences, folders, and tables
- Each expanded subtask row has all placeholders in the task definition replaced by concrete instance variable values (no residual placeholder tokens)
- For table blocks, the number of instances equals the number of table rows; for sequence blocks, it equals the number of sequence elements
- Instances derived from preceding tasks' return values match the actual upstream task outputs reported by Watchdog's web-interface monitoring

## Limitations

- The paper reports no quantitative threshold or benchmark for process block expansion; correctness is judged structurally, not numerically
- Some example workflows require modification or external tools (e.g. example_execution_environments.xml 'requires modifications'; workflow2 needs bwa and ContextMap2 installed and configured)
- The example must first be generated with ./helper_scripts/configureExamples.sh; raw repository checkout does not include configured examples
