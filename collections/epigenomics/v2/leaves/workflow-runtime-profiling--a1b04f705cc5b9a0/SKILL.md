# workflow-runtime-profiling

## Summary

Quantifies the wall-clock overhead that a workflow management system (Watchdog or Snakemake) adds on top of the summed runtimes of its executed tasks, by scaling sample counts and subtracting total task runtime from total execution time. It demonstrates that WMS overhead is negligible relative to actual task runtime.

## When to use

Use when benchmarking a workflow management system's scheduling overhead: you have a runnable Watchdog workflow XML (or an equivalent Snakemake rule chain) and need to measure how much time the WMS itself adds versus the tasks it executes across increasing sample counts.

## When NOT to use

- The goal is to benchmark the performance of the individual analysis tasks themselves (e.g. mapper speed) rather than the overhead added by the workflow management system around them
- The workflow is not managed by a WMS at all (a standalone script has no scheduling overhead to isolate)
- You need exact per-module CPU/memory attribution rather than wall-time overhead of the WMS scheduling layer

## Inputs

- Runnable Watchdog workflow XML file (e.g. from the shipped examples, configured via helper_scripts/configureExamples.sh)
- Sets of input samples across a range of sample counts
- Snakemake Snakefile re-implementing the same task chain with filename-based dependency inference

## Outputs

- wms_overhead_benchmark.csv: per-sample-count overhead (total wall time minus summed task runtimes) for Watchdog and Snakemake
- Per-step execution reports generated by reportGenerator.jar

## How to apply

Configure the shipped example workflows with ./helper_scripts/configureExamples.sh so a runnable workflow XML exists, then execute the Watchdog workflow repeatedly with ./watchdog.sh -x <xml-file> while scaling the number of input samples; the distributed jar files are built for Java 11 and are called internally by the bash scripts. Extract per-step execution reports with reportGenerator.jar, which provides basic reporting of steps performed during workflow execution. Re-implement the identical task chain as Snakemake rules — Snakemake allows definition of tasks based on rules and automatically infers dependencies between tasks by matching filenames — and run it over the same sample sets. For each sample count, compute WMS overhead as total wall time minus the summed task runtimes for both systems and write the comparison to wms_overhead_benchmark.csv. The acceptance check is that measured overheads for both Watchdog and Snakemake remain negligible relative to total task runtime across the sample-count range, matching the trend reported in Additional file 4 of the paper.

## Examples

```
./helper_scripts/configureExamples.sh -i /path/to/watchdog && ./watchdog.sh -x /path/to/watchdog/examples/workflow1_basic_information_extraction.xml
```

## Evaluation signals

- Measured Watchdog overhead (total wall time minus summed task runtimes) is negligible relative to total task runtime across the sample-count range
- Measured Snakemake overhead on the identical task chain shows the same negligible-overhead trend as Watchdog
- reportGenerator.jar output lists per-step execution reports for every workflow step run at each sample count
- The qualitative trend matches the comparison reported in the paper's Additional file 4
- Both systems are run over identical sample sets so the overhead comparison is apples-to-apples

## Limitations

- The jar files are built for Java 11; calling the jar directly (java -jar jars/watchdog.jar) is discouraged because a CTRL+C signal is forwarded to all child processes, which might cause errors on locally running tasks
- The comparison is qualitative ('negligible'); the exact overhead numbers depend on the sample counts and task chain chosen, and no absolute threshold is defined
- Some shipped example workflows need modifications or external tools (e.g. example_docker.xml requires docker with bowtie2; workflow2_differential_gene_expression.xml needs bwa and ContextMap2 configured)
