# wms-execution-overhead-benchmarking

## Summary

A benchmarking procedure that quantifies the computational overhead (total wall time minus summed task runtimes) of a workflow management system — comparing Watchdog against Snakemake — and shows it is negligible relative to actual task runtimes, mirroring the trend reported in the article's Additional file 4.

## When to use

Use when evaluating whether adopting a workflow management system (e.g., Watchdog or Snakemake) adds measurable runtime cost over raw task execution, by scaling input sample counts and separating scheduling overhead from task compute time.

## When NOT to use

- The goal is functional workflow validation (e.g., verifying module integrity or workflow XML correctness via moduleValidator.jar/workflowValidator.jar) rather than runtime overhead measurement
- Only a single fixed sample count is available — scaling the sample count is required to observe the overhead trend relative to task runtime
- The tasks under comparison are not re-implemented identically across the two systems; comparing non-equivalent task chains invalidates the overhead comparison

## Inputs

- Configured Watchdog workflow XML (e.g., example_dependencies.xml from the shipped examples)
- Task-chain input datasets at multiple sample-count scales
- Equivalent Snakemake Snakefile re-implementing the same task chain with filename-matched dependencies

## Outputs

- wms_overhead_benchmark.csv with per-sample-count Watchdog and Snakemake overhead (total wall time minus summed task runtimes)
- Per-step execution reports generated by reportGenerator.jar

## How to apply

Configure a runnable workflow XML from the shipped examples using ./helper_scripts/configureExamples.sh pointed at the Watchdog installation folder. Execute the Watchdog workflow repeatedly with ./watchdog.sh -x <xml-file> while scaling the number of input samples; the Java 11 jar files (watchdog.jar) are called internally by the bash scripts. Extract per-step execution reports with reportGenerator.jar, which provides basic reporting of the steps performed during workflow execution. Re-implement the same task chain as Snakemake rules — Snakemake automatically infers dependencies between tasks by matching filenames — and run it over identical sample sets. For each sample count, compute WMS overhead as total wall time minus summed task runtimes for both systems and write the comparison to wms_overhead_benchmark.csv; the acceptance check is that both overheads remain negligible relative to total task runtime across the sample-count range.

## Related tools

- **Watchdog** (Workflow management system whose scheduling overhead is benchmarked; workflows are executed via ./watchdog.sh -x <xml-file>) — github.com/klugem/watchdog
- **Snakemake** (Python-based WMS used as the comparison system; tasks defined as rules with dependencies inferred automatically by matching filenames)
- **Java** (Runtime environment for the distributed Watchdog jar files (built for Java 11) called internally by the bash scripts)

## Examples

```
./helper_scripts/configureExamples.sh -i /path/to/watchdog && ./watchdog.sh -x examples/example_dependencies.xml && java -jar jars/reportGenerator.jar
```

## Evaluation signals

- wms_overhead_benchmark.csv exists with one row per sample count covering both Watchdog and Snakemake
- Measured overhead for both systems stays negligible relative to total summed task runtime across the full sample-count range
- The overhead trend qualitatively matches the comparison reported in the paper's Additional file 4
- Per-step execution reports from reportGenerator.jar reconcile with the summed task runtimes used in the overhead calculation
- The Snakemake run resolves the same dependency structure as the Watchdog workflow (validated by matching filenames)

## Limitations

- Overhead conclusions hold for this task chain and sample scaling and may not transfer to workflows with many trivially short tasks where scheduling cost dominates
- Watchdog requires JDK 11 or higher (JavaFX SDK 11+ for the GUI/moduleMaker), so environments with older Java cannot run the distributed jar files
- The article/README does not state a specific Watchdog version number or changelog, so reproducibility of exact overhead numbers depends on the release used
