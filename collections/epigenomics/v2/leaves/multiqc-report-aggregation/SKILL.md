# multiqc-report-aggregation

## Summary

Aggregate the per-sample quality-control outputs generated by CIPHER's five-step NGS pre-processing stage (FastQC, trimming, mapping, visualization, QC) into a single consolidated report via MultiQC, giving one at-a-glance QC view across all datasets in the run.

## When to use

Reference for combining multiple per-sample NGS quality-control outputs (FastQC, trimming/mapping stats) from a Nextflow/CIPHER run into one aggregated MultiQC report instead of inspecting each QC file individually.

## When NOT to use

- The config mixes single-ended and pair-ended data in one file — the README states 'CIPHER DOES NOT HANDLE THIS USE-CASE YET', so the aggregated QC step cannot be reached reliably
- You only need a subset of pipeline steps (e.g. MultiQC alone) — the article notes 'CIPHER currently only runs entire workflows, but we are aware that individuals may prefer to use only a subset of tools'
- Input data are not NGS datasets supported by CIPHER (ChIP-seq, RNA-seq, MNase-seq, DNase-seq, GRO-seq, ATAC-seq); e.g. GWAS or de novo transcriptome assembly have no pipeline

## Inputs

- Per-sample FastQC output directories (fastqc_report.html, fastqc_data.txt) from raw sequence evaluation
- Trimming/adapter-removal statistics from BBDuk on gzipped FASTQ inputs
- Alignment statistics from BBMap/BWA/Bowtie2/STAR/Hisat2 mapped BAM files
- CIPHER config file (tab-separated, 5 columns single-end or 6 columns pair-end: MergeID, SampleID, FASTQ path(s), InputID, Mark)

## Outputs

- A single aggregated MultiQC QC report (html/pdf) in the './report' output directory
- Gzipped trimmed FASTQ files and sorted BAM files with alignment statistics alongside the aggregated report

## How to apply

Run CIPHER's fixed pre-processing stage — raw sequence evaluation (FastQC), read trimming and adapter removal (BBDuk, defaults filtering reads with mapq < 20 or length < 10 after mapping), read mapping (BBMap by default; bwa, bowtie2, star, hisat2 selectable via --aligner), visualization track generation, and quality-control assessment. CIPHER executes these via a Nextflow workflow (cipher.nf) inside Singularity containers, so all tools run with consistent environments. Because CIPHER's stage-1 pipeline incorporates 'a number of quality control tools', the per-sample QC outputs accumulate across datasets; at the end of the stage, MultiQC scans the workflow's output directory (default './report', override with --outdir) and aggregates the individual QC reports into a single interactive HTML (or PDF-style) summary. Rationale: a consolidated MultiQC report makes cross-sample biases, contaminations, and errors visible in one artifact, which is the final 'extensive quality control assessment' step of CIPHER's pipelines.

## Related tools

- **MultiQC** (Aggregates the per-sample FastQC, trimming, mapping, and QC outputs of CIPHER's stage-1 pipeline into a single interactive report in the output directory)
- **FastQC** (Generates the raw-sequence-evaluation QC reports that MultiQC later aggregates)
- **Nextflow** (Workflow language that orchestrates the QC steps whose outputs MultiQC aggregates (cipher.nf entry point)) — https://www.nextflow.io/
- **CIPHER** (Platform whose fixed pre-processing stage (evaluation, trimming, mapping, visualization, QC) produces the artifacts fed into MultiQC) — github.com__c-guzman__cipher-workflow-platform

## Examples

```
nextflow run cipher.nf -with-singularity <cipher.img> --mode chip --config <CONFIG> --fa <FASTA> --gtf <GTF> --lib s --readLen 75
```

## Evaluation signals

- A single MultiQC report (html/pdf) exists in the './report' directory (or --outdir) after the run completes
- The report aggregates QC for every sample listed in the tab-separated config file (one entry per SampleID, single-end 5-column or pair-end 6-column)
- Per-sample QC modules (FastQC module, trimming/adapter stats, alignment statistics from the sorted BAMs) are all represented in the aggregated report
- The run was launched with a valid --mode (chip, rna, gro, mnase, dnase, or atac) and the workflow completed without abruptly ending due to memory exhaustion (use -qs <INT> when not on a cluster)
- Trimmed gzipped FASTQs and sorted BAMs are present in the same output directory, confirming MultiQC aggregated a complete stage-1 run rather than a partial one

## Limitations

- CIPHER does not handle mixed single-end/pair-end data in one config file, so QC aggregation fails on such runs
- When running outside Singularity, all pipeline software must be installed locally or the QC steps MultiQC aggregates will not be produced
- Over-parallelizing on a non-cluster machine can make the workflow 'abruptly end because it runs out of memory', leaving the MultiQC report missing or stale
